# 需求对齐

目标：说明当前有效的需求做到了没有；需求被后续要求改掉时，保留改动的依据。

## 每个条目都保留

`requirements.json` 中的**每个条目恰好出现一次**，不重复、不遗漏、不新增条目。`requirementItemId` 照抄给定的 `itemId`，不要自己编号（如 REQ-1）。需求全文与条目的先后顺序都来自冻结输入。

| status | 含义 | 必须写 |
|---|---|---|
| `implemented` | 这一条在本次改动中做到了 | `codeRefs` 指向实现它的代码 |
| `partial` | 做了一部分 | `codeRefs` 指向已做的部分，`note` 写缺了什么 |
| `not-found` | 在本次审查范围内没找到实现 | `note` 写查了哪里 |
| `unclear` | 实现证据不足，或需求之间的关系不明确 | `note` 写缺什么信息 |
| `superseded` | 被后面的条目明确修改或取消（界面称「已调整」） | `supersededBy`（填目标条目的 `itemId`）、`supersededQuote`；`note` 简述怎样调整；`codeRefs` 输出空数组 |

- `not-found` 只表示「在这次交付的改动和审查包里没找到」，不表示整个仓库都没有实现。
- 拿不准就用 `unclear`，不要为了看起来完整而判 `implemented`。
- `note` 写具体内容，例如「导出按钮在零问题时仍被禁用，需求要求可导出」，不写「部分实现」这种重复状态的话。

## 已调整（`superseded`）

**只在新旧要求不能同时满足时使用**：满足后面的要求，就必须放弃前面那条。代码能同时满足两条的，属于补充或细化，两条分别判断。

- 「后面」按来源的 `order` 判断；同一来源内按条目的 `start` 判断。不按捕获时间或文件日期判断。`supersededBy` 必须指向同一快照内更靠后的条目，不能指向自己。
- `supersededQuote` 逐字照抄目标条目中表达修改或取消的**完整语句或分句**（与原文完全一致，不改字，不改标点），例如「不做 PDF 了，改成 HTML」；不要只摘「PDF」「不要」这类孤立的词。`note` 说明这条后续要求为什么针对当前条目，不要把引文改写成用户没说过的话。
- 算已调整的例子：
  - 明确取消：「前面说的导出 PDF 先不做了」「删除按钮不要了」；
  - 明确改写：「不做 PDF 了，改成 HTML」「全屏模式取消，改为原地展开」；
  - 互斥的设定：「默认排序原来按创建时间，现在改成按最近活动」。
- 不算已调整的例子（两条都要分别判断）：
  - 追加：「导出支持 Markdown」之后又说「再加一个导出 HTML」；
  - 细化：「添加删除按钮」之后又说「删除时要二次确认」；
  - 修复：「支持邮箱校验」之后又说「修复大写字母校验报错」；
  - 扩展：「macOS 支持 Cmd+K」之后又说「Windows 用 Ctrl+K」；
  - 局部调整：「表单含姓名、年龄、地址」之后又说「年龄改为只读」。前一条仍要判断，不能整条标为已调整。
- 后加、实现困难、代码里没做，都不是已调整的理由。举例、引用别人的说法、假设、还没定下来的选项，都不当作用户已确认取消。
- 只改掉旧条目的一部分时，不能把含有其他独立要求的整条标为已调整；无法分开判断时，用 `unclear` 并说明。
- 关系不明确、先后不确定、调整依据被截断时，用 `unclear`。不要为了减少未对齐的数量而标 `superseded`。
- 被调整的条目不再判断实现；后面的条目照常判断。允许 A→B→C 这样的链，每条只引用直接调整它的那一条，不跳过中间的要求。
- 「需求已调整」不等于「代码已改完」。

## 需求之外的改动（`extras[]`）

- 列出与任何当前有效的需求都无关、但改变了行为的改动，每条带引用。
- 需求被取消后，代码里仍保留的行为，不能借已调整的旧需求免于列出。
- 测试、类型、为实现需求必需的重构，不算需求之外。
- 不因需求的状态删掉实际存在的功能与文件说明。

## 没有需求依据时

`overview.requirementStatus` 写 `no-requirement`，`alignment` 与 `extras` 都输出空数组。

## 自查

核对编号、先后、引文与所指对象。原文片段能对上，只证明出处；新旧要求之间的关系仍是你的推断。
