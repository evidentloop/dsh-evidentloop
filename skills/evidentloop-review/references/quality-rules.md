# 质量规则

所有说明、对齐、问题的文字都适用。其中第 2 条（引用）由插件机器校验：缺引用或引用无效的说明会被删除，记为「证据未通过校验」，这次审查也不算完整；其余各条靠你遵守，并在质量试验中由人工评分。

1. **不写套话。**没有具体对象的句子不合格，例如「优化了逻辑」「提升了可维护性」「增强了健壮性」「进行了重构」。改成说清对象和变化：「`collectFiles()` 改为跳过 `.gitignore` 忽略的未跟踪文件」。
2. **每条都有出处。**功能、逐文件要点、影响、需求外改动里的每条说明，都至少带一个有效引用；可选的说明找不到依据就不写。必需的记录不能因此删掉：每个审查目标文件的记录、每个需求条目的对齐记录都要保留，判断不了时按 `unclear` 处理。
3. **不编造。**看不出意图时写「未能从代码判断」；不推测审查包之外的代码；不把需求依据里没有的当成需求。用客观的陈述句说代码改了什么，不揣测作者的心思（如「作者意在…」）；基于冻结代码的推断可以写，但要标明是推断。
4. **先结论后细节。**功能列表说结论，细节放进逐文件要点。
5. **单列没做的。**未实现或部分实现的需求、需求之外的改动，必须写进 `alignment` 与 `extras`，不能只在别处顺带一提。
6. **一件事只说一次。**同一个改动不在功能和逐文件要点里用同样的话重复。
7. **问题不是建议。**风格、命名、可选改进不进问题清单（`findings`）。
